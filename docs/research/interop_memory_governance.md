## 1. Model Context Protocol (MCP) and A2A

### 1.1 Current spec version and what changed

- **Current protocol revision: `2026-07-28`** (released 28 July 2026). Prior revisions: 2025-11-25, 2025-06-18, 2025-03-26, 2024-11-05. [verified via the official release post https://blog.modelcontextprotocol.io/posts/2026-07-28/ and the spec repo https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/basic/transports/streamable-http.mdx]
- Headline changes in 2026-07-28 (from the release post):
  - **Statelessness by default.** The `initialize`/`initialized` handshake and `Mcp-Session-Id` are retired; every request carries its own protocol version (`MCP-Protocol-Version` header, mirrored in `_meta`) and client info. Any server instance behind a round-robin LB can serve any request. Optional `server/discover` exposes capabilities. A server that needs state returns an explicit handle from a tool.
  - **Multi Round-Trip Requests (MRTR, SEP-2322).** Server-initiated elicitation/sampling/roots no longer need a held-open stream; the server returns `input_required` and the client retries with answers attached.
  - **Transport headers for gateways.** Every POST must carry `Mcp-Method`; `Mcp-Name` is required for `tools/call`, `resources/read`, `prompts/get`; tool params flagged `x-mcp-header` are mirrored into `Mcp-Param-{Name}` so gateways can route and rate-limit without parsing bodies. Mismatch between header and body returns 400 with error `-32020`.
  - **Cacheable list results** (`ttlMs`, `cacheScope`, deterministic order).
  - **Authorization hardening**: RFC 9207 `iss` required from AS and validated by clients; Dynamic Client Registration deprecated in favour of **Client ID Metadata Documents (CIMD)**.
  - **Formal extensions framework**: Tasks (`tasks/get`, `tasks/update`, `subscriptions/listen`), MCP Apps, and Enterprise Managed Authorization are now extensions.
  - **Deprecations**: Roots, Sampling, Logging deprecated (kept ≥12 months); legacy HTTP+SSE transport (2024-11-05) deprecated with a year-long transition.
  - SDK support at release: TypeScript, Python, Go, C# (Tier 1); Rust in beta.

### 1.2 Streamable HTTP transport (2026-07-28) [verified from spec repo]

- Single HTTP endpoint (e.g. `https://host/mcp`) that MUST accept POST. Each JSON-RPC request/notification is its own POST; client sends `Accept: application/json, text/event-stream`; notifications get `202 Accepted`; requests get either a single JSON body or an SSE stream carrying request-scoped notifications followed by the final response. Streams are not resumable; closing a stream = cancellation.
- No standalone GET stream and no protocol-level sessions in this revision: servers that only implement 2026-07-28 return 405 to GET/DELETE and ignore `Mcp-Session-Id`/`Last-Event-ID`.
- Security: servers MUST validate `Origin` (DNS-rebinding defence, 403 on bad origin), local servers should bind 127.0.0.1, servers SHOULD implement authentication; `X-Accel-Buffering: no` recommended on streams.
- Backward compatibility: clients may send a modern request first; a 400 with a recognised modern JSON-RPC error means "modern server"; an empty/unknown body means fall back to `initialize` (2025-03-26..2025-11-25 semantics with sessions and GET streams); 400/404/405 with unknown body → try the legacy GET `endpoint` event (2024-11-05 HTTP+SSE).

### 1.3 Authorization model

- MCP servers are OAuth 2.1 **resource servers**; they publish RFC 9728 Protected Resource Metadata that points clients to the authorization server; clients MUST use PKCE (S256) and RFC 8707 resource indicators; servers MUST validate that tokens were issued for them (audience) and MUST NOT pass through the client's token to upstream services. In 2026-07-28, CIMD (client_id is an HTTPS URL the AS fetches) is the SHOULD path and Dynamic Client Registration is MAY/deprecated; RFC 9207 `iss` validation is required. [search-only for exact MUST/SHOULD levels: https://modelcontextprotocol.io/specification/draft/basic/authorization, https://ssojet.com/blog/mcp-authentication-oauth-tokens-security-ai-connections, https://scalar.com/learn/mcp/mcp-oauth; Keycloak's MCP AS guide https://www.keycloak.org/securing-apps/mcp-authz-server]
- Implication for a retrieval engine: the MCP server must receive a **per-user** access token (so retrieval can be permission-trimmed, see §3) and must never forward that token to Qdrant/NIM/etc.; mint service credentials instead and carry the user identity as claims.

### 1.5 Hosting an MCP server inside a FastAPI app (Python)

Two viable libraries, both support 2026-07-28:

1. **Official SDK `mcp` 2.3.0** (PyPI, released 2 Oct 2026; 1.x is in maintenance; `pip install mcp` now installs 2.x; requires Python 3.11+) [verified https://pypi.org/project/mcp/]. In v2 the high-level class was renamed `FastMCP` → **`MCPServer`** (`from mcp.server import MCPServer`), `LATEST_PROTOCOL_VERSION = "2026-07-28"`; `stateless_http`/`json_response` moved from the constructor to `run()`/`streamable_http_app()`; you build routes at module level and **enter the session manager in the host app's lifespan** (a mounted sub-app's lifespan never runs, otherwise "Task group is not initialized"). Server auth params `auth`, `token_verifier`, `auth_server_provider` are unchanged from v1. [verified https://raw.githubusercontent.com/modelcontextprotocol/python-sdk/main/docs/migration.md]
2. **FastMCP (jlowin) 4.1.0** (PyPI, 8 Oct 2026; 4.0.0 on 31 Aug 2026) [verified https://pypi.org/project/fastmcp/]. FastAPI pattern [verified https://raw.githubusercontent.com/jlowin/fastmcp/main/docs/integrations/fastapi.mdx]:
   ```python
   mcp_app = mcp.http_app(path="/")          # Streamable HTTP ASGI app
   app = FastAPI(lifespan=mcp_app.lifespan)  # lifespan is REQUIRED
   app.mount("/mcp", mcp_app)                # endpoint = /mcp
   ```
   Use `combine_lifespans(...)` when you already have one; do not put app-wide `CORSMiddleware` on a combined app that mounts an OAuth-protected server (breaks `.well-known`). `FastMCP.from_fastapi(app)` can auto-convert routes but hand-curated tools work better with LLMs. FastMCP ships OAuth proxy/JWT verifier auth providers (docs at gofastmcp.com; its README only mentions the Prefect "Horizon" enterprise gateway for SSO/RBAC).
   - The third-party `fastapi-mcp` adapter has had no release since v0.4.0 (Jul 2025) [search-only https://www.agenticwire.news/article/fastmcp-vs-fastapi-mcp]; avoid.

Recommendation: mount with FastMCP 4.x (fastest path, good auth providers) or the official `mcp` 2.x `MCPServer` if you want zero extra deps; expose `/mcp` on the same FastAPI process, stateless, behind the same OAuth/JWT verifier used by the REST API, and validate `Origin`.

### 1.6 A2A (Agent-to-Agent) — status and relevance

- Linux Foundation project (Google contributed Jun 2025), Apache-2.0. **v1.0.0 released 12 Mar 2026** (breaking changes, `tasks/list`), **v1.0.1 on 28 May 2026** (bug fixes). Agent Card at `/.well-known/agent-card.json`; JSON-RPC 2.0 over HTTPS with gRPC and HTTP+JSON bindings; signed Agent Cards. [verified https://github.com/a2aproject/A2A/releases, https://github.com/a2aproject/A2A]
- Adoption: >150 organisations, integrated in Google/Microsoft/AWS platforms (LF press, Apr 2026) https://www.linuxfoundation.org/press/a2a-protocol-surpasses-150-organizations-lands-in-major-cloud-platforms-and-sees-enterprise-production-use-in-first-year
- Relevance to a retrieval engine: **low at v1**. A2A is for agent↔agent delegation; our engine is a *tool/knowledge source*, which is exactly MCP's remit. Expose MCP first; consider publishing an Agent Card only if we later ship a "research agent" that other agents delegate long-running tasks to (Glean already supports adding third-party agents as sub-agents, Jul 2026 release notes).

**What is "standard" now (Oct 2026):** the CoALA-style split **episodic + semantic + procedural** (LangMem names it explicitly; Letta implements it as blocks/archival/files; Mem0 as user/session/agent scopes), with a **temporal/bi-temporal knowledge graph** (Graphiti) as the differentiator for "facts that change". Every library scopes memory by `user_id` (+ `agent_id`/`session`), exposes `add`/`search`/`get_all`/`delete`, and does extraction with an LLM at write time. Benchmark numbers (LoCoMo/LongMemEval) are all vendor-measured and disputed [search-only https://atlan.com/know/best-ai-agent-memory-frameworks-2026/].

**Recommendation for us:** implement a thin `MemoryStore` interface (`add(user_id, scope, messages) / search(user_id, query, k) / list / delete`) backed by our own Qdrant collection with payload fields `{tenant_id, user_id, scope: episodic|semantic|procedural, valid_from, valid_to, source_episode_id}`, so Mem0 (Apache) or Graphiti (Apache) can be swapped in later. Do not take a hard dependency on LangMem (stale) or Letta (runtime, not a library).

## 3. Permission-aware retrieval, document-level ACL trimming, multi-tenancy

How the reference systems do it:

- **Glean**: connectors mirror source ACLs (users/groups) into the index; every query is filtered against the asker's identity and group memberships; AI answers and citations only draw from authorised content; identity synced from IdP; permission changes propagate on delta sync; agents/MCP run as the signed-in user with no escalation. [search-only https://docs.glean.com/security/security-principles, https://docs.glean.com/administration/platform/mcp/security, https://docs.glean.com/connectors/connectors-power-glean]
- **Azure AI Search / Foundry IQ**: two mechanisms. (a) **Built-in document-level access control (preview, REST 2025-05-01-preview+)**: indexers for ADLS Gen2 and SharePoint ingest permission metadata (`userIds`, `groupIds`, `rbacScope`); at query time the caller's Entra token is passed in `x-ms-query-source-authorization` and the service filters (container RBAC first, then ACL entries; ABAC not evaluated). SharePoint ACLs are captured only at initial indexing — re-index on permission change. Elevated read is only for `Search Index Data Contributor`. (b) **Security filters** (GA, classic): store principal ids in a filterable string collection and AND a filter `security_ids/any(g: search.in(g, 'group1,group2'))` into every query. Foundry IQ knowledge bases forward the same header; for remote SharePoint knowledge sources nothing is indexed and SharePoint enforces permissions at query time via the Copilot Retrieval API; Blob/OneLake sources don't support full ACL ingestion. [search-only https://learn.microsoft.com/en-us/azure/search/search-document-level-access-overview, https://learn.microsoft.com/en-us/azure/search/search-indexer-sharepoint-access-control-lists, https://learn.microsoft.com/en-us/azure/search/search-indexer-access-control-lists-and-role-based-access, https://docs.azure.cn/en-us/search/search-security-trimming-for-azure-search, https://techcommunity.microsoft.com/blog/azure-ai-foundry-blog/announcing-enterprise-grade-microsoft-entra-based-document-level-security-in-azu/4418584]
- **Amazon Bedrock Knowledge Bases**: (a) **Metadata filtering** — tag each document with `tenant_id`/`user_id`/groups at ingestion and apply a filter derived from the *verified* identity (Cognito JWT claims) on every retrieve, including every sub-query in agentic retrieval; AWS recommends the pooled (one KB + filters) model for many small tenants and silo (KB per tenant) only for strict isolation; optional Cedar policies via Verified Permissions, fail-closed. (b) **Managed Knowledge Base (GA Jul 2026)** with native SharePoint/Confluence/Google Drive/OneDrive/S3/web connectors does **document-level ACLs**: candidates filtered by ACLs synced at last crawl, then **re-verified in real time** against the user's current permissions; SharePoint ACLs need Entra app-only auth (`aclEnabled`); web crawler has no ACLs; Sep 2026 added `CheckIngestedDocumentAcl` / `GetIngestedDocumentAcl` debugging APIs. AWS explicitly says this is "ACL-aware filtering, not a security boundary — your application authenticates users and passes verified identity". [search-only https://aws.amazon.com/blogs/machine-learning/multi-tenancy-in-rag-applications-in-a-single-amazon-bedrock-knowledge-base-with-metadata-filtering/, https://aws.amazon.com/blogs/architecture/secure-multi-tenant-rag-with-amazon-bedrock-and-verified-permissions/, https://docs.aws.amazon.com/bedrock/latest/userguide/kb-managed-ds-sharepoint-acl.html, https://aws.amazon.com/blogs/machine-learning/build-enterprise-search-for-agents-with-amazon-bedrock-managed-knowledge-base/]
- **Onyx (ex-Danswer)**: per-connector access mode `private | public | Auto Sync Permissions`; permission sync code lives under `backend/ee/onyx/external_permissions/` (Confluence, Google Drive, SharePoint, Slack, Jira, GitHub, Salesforce, Teams, Gmail…) and is **Enterprise-licensed**; the MIT community edition has no permission sync. [search-only https://docs.onyx.app/admins/connectors/overview, https://docs.onyx.app/changelog, https://www.teamazing.com/blog/onyx-ai-enterprise-review-2026/]
- **Qdrant**: official guidance is **one collection, payload-based partitioning**: keyword payload index on the tenant field with `is_tenant: true` (Qdrant ≥1.11; co-locates a tenant's vectors for sequential I/O), every query carries a `must` filter on the tenant field; optionally HNSW `m=0, payload_m=16` to build per-tenant graphs (do NOT if you also run global searches); for very large/uneven tenants use user-defined sharding or **tiered multitenancy (Qdrant ≥1.16)**: shared fallback shard for small tenants, dedicated shards for big ones. The index is a performance hint, not an authorization control — a query without the filter is not made safe. [search-only but official pages https://qdrant.tech/documentation/manage-data/multitenancy/, https://qdrant.tech/documentation/examples/multitenancy/]

**Recommended pattern for us (converges with all of the above):**

1. **Identity in, never trust the client.** Every REST/MCP call carries an OAuth/JWT bearer; derive `tenant_id`, `user_id`, `groups[]` from verified claims (or from an IdP group lookup cached per request). MCP tools do not accept a free-form `user_id`.
2. **ACLs stored on every chunk at ingest** as payload: `tenant_id` (keyword, `is_tenant=true`), `allowed_principals[]` (user ids + group ids + `public`), `denied_principals[]` optional, `source`, `doc_id`, `acl_version`, `acl_synced_at`.
3. **Mandatory filter injection** in one place (the retriever), for *every* vector/BM25/hybrid/agentic sub-query: `must: tenant_id == T` AND `allowed_principals any-of {user, groups..., public}` AND `not denied_principals any-of {...}`. Post-filtering is never used as the only control (it leaks via top-k starvation and timing).
4. **Permission sync is a first-class connector concern**: each connector has `fetch_acl(doc)` plus a `permission_sync` job (delta where the source supports it), and an optional **real-time re-check** hook (Bedrock-style) for high-sensitivity sources.
5. **Fail closed**: if the group resolver or ACL service is unavailable, return no results (Bedrock/Verified Permissions pattern).
6. **Elevated-read role** only for admin/debug endpoints; ship `check_document_acl(doc_id, user)` and `get_document_acl(doc_id)` debugging endpoints (Bedrock Sep 2026 precedent).
7. **Multi-tenancy**: one Qdrant collection per deployment with payload partitioning and tiered multitenancy for big tenants; separate collections only for regulated tenants demanding physical isolation.

## 5. Observability and evaluation in production

- **OpenTelemetry GenAI semantic conventions**: still **Development (not Stable)** as of Oct 2026. In core semantic-conventions **v1.42.0 (12 Jun 2026)** the GenAI conventions were deprecated-in-place and **moved to a dedicated repo `open-telemetry/semantic-conventions-genai`**, which has no tagged release/schema URL yet. **What to log per query (one trace, OTel GenAI names where they exist):**

- Root span `invoke_agent`/request: `tenant_id`, `user_id` (hashed), `session_id`, `conversation_id`, `gen_ai.conversation.id`, client (`ui|api|mcp`), `request_id`, latency, status, cost.

- `execute_tool` spans for MCP tool calls (tool name, args hash, result size).
- Guardrail spans: input/output classifier verdicts, groundedness score, PII entities redacted (counts only).
- Post-hoc: citation set (chunk ids actually cited), user feedback, sampled RAGAS faithfulness / groundedness scores attached as Langfuse scores.

## 9. Prioritised feature list for an enterprise retrieval engine

### Must have at v1
1. **OAuth/JWT identity on every call + tenant & ACL payload filters injected in the single retriever path** — without this nothing else is enterprise-grade (Glean/Azure/Bedrock/Qdrant all converge here).
2. **Chunk-level ACL ingestion + permission-sync job per connector, fail-closed** — ACLs must come from the source, not the app.
3. **MCP server (Streamable HTTP, 2026-07-28, stateless) exposing `retrieve` with OAuth 2.1/RFC 9728 metadata** — the universal plug for Claude/Copilot/Foundry/agents; one tool, like Foundry IQ.
4. **Connector ABC + first connectors: file upload, web crawl, S3/Blob, SharePoint/OneDrive, Google Drive, Confluence, Slack** — the sources every RFP lists; reuse Unstructured (Apache) for parsing.
5. **Hybrid retrieval + NIM rerank with `input_type` handled correctly and a model fallback chain (410/429 aware)** — NIM retires endpoints with weeks of notice and caps the free tier at ~40 RPM.
6. **Inline citations with deterministic citation-id validation and highlight-to-source** — the one NotebookLM feature every user now expects.
7. **OTel traces per query (retrieval spans with chunk ids/scores, token usage, cost) shipped to Langfuse v4 via OTLP** — you cannot debug or price RAG without it; GenAI semconv names are usable even though Development.
8. **Input/output guardrails: Prompt Guard 2 or Prompt Shields on user input, spotlighting/datamarking of retrieved chunks, PII redaction (Presidio) of logs** — indirect injection via documents is the top RAG-specific threat.
9. **Multi-tenant Qdrant layout (payload partitioning, `is_tenant`, tiered multitenancy)** — cheap to do up front, expensive to retrofit.
10. **Source summaries + follow-up question suggestions + notebook/collection scoping** — low cost, high perceived value, and scoping doubles as a filter.

### Should have at v2
1. **Memory layer (episodic/semantic/procedural, user-scoped) behind a `MemoryStore` interface with Mem0/Graphiti adapters** — personalisation is now expected; keep it swappable.
2. **Deep research mode (iterative plan → corpus + web search → cited report saved as a new source)** — NotebookLM/Perplexity/Glean all shipped it in 2025–26.
3. **Report/document generation (briefing doc, FAQ, timeline, slides, data tables → CSV/XLSX)** — SurfSense/NotebookLM level output.
4. **Groundedness scoring (sampled RAGAS faithfulness online; optional Azure/Bedrock grounding checks) surfaced in Langfuse and as "unsupported claim" UI flags** — moves from "we cite" to "we verify".
5. **Real-time ACL re-check for high-sensitivity sources + ACL debug endpoints (`check_document_acl`)** — Bedrock Managed KB precedent; auditors ask for it.
6. **Connector expansion: Notion, Jira, GitHub, Gmail/Outlook/IMAP, Teams, Zendesk, Salesforce** — second tier of RFP sources.
7. **NeMo Guardrails retrieval/output rails config (Colang 1.0) and Llama Guard 4 content classification** — policy-as-config instead of hard-coded checks.
8. **Structured-output fallback chain (`response_format` → `guided_json` → `nvext`) and tool-calling abstraction across NIM models** — needed as soon as we do extraction or agents.
9. **Mind maps and audio overview (TTS, local or hosted)** — recognisable NotebookLM features; cheap once report generation exists.

### Nice later
1. **A2A Agent Card for a "research agent"** — only matters once other agents delegate long-running tasks to us.
2. **Video overviews / cinematic outputs, flashcards & quizzes** — consumer-grade polish, little enterprise pull.
3. **Microsoft Graph/Copilot connector publishing our index into M365** — only for Copilot-first shops.
4. **CaMeL-style capability separation for write-capable tools** — required only when agents can take actions, not for read-only retrieval.
5. **Automated Reasoning (formal policy) checks à la Bedrock** — niche, regulated-domain feature.
6. **Model Council / multi-model parallel answers** — Perplexity Max gimmick; costly on a 40-RPM budget.
7. **Event-triggered background agents on content change (Glean Jul 2026)** — valuable, but depends on v2 connectors + memory being solid.
